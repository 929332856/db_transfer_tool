# 程序全面检查报告

检查日期：2026-08-13  
检查对象：`meiqiu_db` 当前工作区版本  
检查结论：程序主体可以通过 Python 编译检查，但在安全边界、跨数据库一致性、任务并发、错误处理、前端安全和工程化方面存在多项需要整改的问题。

## 一、审查说明

### 1. 审查范围

- 后端核心逻辑：`db_transfer_eel.py`
- Flask 路由：`app/__init__.py`、`app/routes/__init__.py`
- 启动入口：`main.py`
- 前端：`web/js/main.js`、`web/js/tree_modules/`、相关 HTML/CSS
- 旧/拆分模块：`modules/`
- 发布配置：`build_release.ps1`、`mqdb.spec`

### 2. 审查方法

- 静态检查数据库连接、DDL/DML 拼接、文件操作、任务状态和路由注册逻辑。
- 追踪全量同步、拖拽复制、导出/导入、表设计、备份等主要业务链路。
- 执行 `py -3 -m py_compile db_transfer_eel.py`，通过。
- 执行 `py -3 -m compileall -q app modules db_transfer_eel.py`，通过。
- 检查 Flask 路由注册情况，当前约注册 119 个 API，并发现两个 `/api/ping` 路由。
- 当前环境没有 Node.js，因此未执行 JavaScript 语法检查和前端构建检查。

### 3. 重要前提

当前工作区不是干净工作区，包含已有的用户/历史修改、删除文件和未跟踪文件。本报告基于“当前文件内容”进行判断，不代表所有问题都由最近一次修改引入，也没有回滚或覆盖已有改动。

## 二、架构概览

当前程序同时存在几套运行和业务组织方式：

1. `db_transfer_eel.py` 集中了约 8666 行后端业务，并通过 Eel 暴露函数。
2. `app/routes/__init__.py` 自动收集暴露函数并生成 Flask API。
3. `main.py`、`app/__init__.py` 和 `db_transfer_eel.py` 底部均包含启动或兼容逻辑，存在多入口。
4. `modules/` 中又保留了传输、拖拽复制、导入导出、表设计、表操作等重复实现。
5. 前端使用大量普通 `<script>` 顺序加载、全局变量和字符串拼接 HTML。

这套结构短期便于快速迭代，但会造成“同一个功能有多个实现”“只修了某条入口，另一条入口仍有旧行为”的风险。后续建议明确一个正式入口，并逐步把业务按连接、元数据、DDL、任务调度、导入导出等职责拆分。

## 三、问题等级说明

- **P0**：存在明显的高危安全或数据破坏风险，应立即处理。
- **P1**：可能造成数据丢失、跨库功能失效、任务错乱或严重误操作，应优先处理。
- **P2**：影响功能完整性、可维护性或异常场景稳定性，应纳入近期迭代。
- **P3**：工程质量、体验或长期维护问题，可在核心风险处理后治理。

## 四、问题清单

### A. 安全与数据保护

#### A-01 [P0] 本地 Flask API 无认证，且允许所有来源的 CORS

位置：

- `app/__init__.py:28`：使用 `CORS(app)`。
- `app/__init__.py:84`：监听 `127.0.0.1`。
- `app/routes/__init__.py:201` 附近：自动注册大量 API。

影响：虽然服务只监听本机，但本机其他进程，或能够访问本机端口的恶意网页，都可能调用数据库删除、清空、执行 SQL、Redis 命令等危险接口。当前接口没有令牌、会话或来源校验。

建议：

1. 启动时生成随机 API token，并要求请求头携带 token。
2. 将 CORS 改为明确的允许来源，默认不允许任意来源。
3. 危险操作增加权限分层、二次确认和审计日志。
4. 生产模式禁止直接暴露任意 SQL/Redis 执行接口，或至少增加显式的危险操作开关。

#### A-02 [P1] 自动把暴露函数转换成 HTTP API，暴露范围过宽

位置：`app/routes/__init__.py:170-220` 附近。

影响：自动收集 Eel 暴露函数会把内部辅助函数也转为 API，例如 `_format_oracle_ddl`；同名函数还可能产生路由冲突，实测存在两个 `/api/ping`。随着业务函数增加，API 面会无意扩大，内部实现也会被外部调用。

建议：改为显式 API 白名单；路由名称、HTTP 方法、参数校验和权限在路由层单独声明。内部函数不要通过“是否暴露给 Eel”来决定是否成为 HTTP API。

#### A-03 [P1] 数据库连接密码以明文 JSON 保存

位置：`db_transfer_eel.py:41-42`、`135-201`、`3835-3842` 附近。

影响：配置文件和树节点数据直接保存包含 `pwd` 的连接信息。读取文件、备份配置或其他本地程序都可能获得数据库密码。

建议：Windows 环境优先使用 DPAPI 或 Credential Manager；至少将密码单独加密保存，显示和日志中统一脱敏，并提供密码轮换/清除能力。

#### A-04 [P1] 标识符拼接未进行严格校验或正确转义

位置：`db_transfer_eel.py:1405-1430` 的 `_safe_ident`、`_build_table_ref`。

问题：当前 `_safe_ident` 主要是给名称加包围符，没有对包围符自身进行数据库方言级转义；`database`、`schema`、`table`、字段名等会参与 SQL 拼接。

例如 MySQL 名称包含反引号时，可能形成类似 `` `db`x`.`table` `` 的非法或可被改变语义的 SQL。即使名称通常来自数据库元数据，也不能假定所有输入永远可信。

建议：按数据库类型实现统一的标识符引用函数；对名称做长度、字符和包围符校验，拒绝不符合规则的标识符；值参数继续使用参数化查询，不能用字符串格式化替代。

#### A-05 [P1] 文件名和导出路径存在路径穿越风险

位置：`db_transfer_eel.py:6881`、`6980-6987` 的导出和 `save_import_file`。

问题：用户输入的 `filename` 参与 `os.path.join(BASE_DIR, "temp", filename)` 等路径组合，未看到完整的文件名净化和最终路径约束。

影响：恶意路径可能写入临时目录之外，覆盖不应覆盖的文件；导出路径也可能被利用访问非预期位置。

建议：只接受文件名而不是路径；使用 `os.path.basename`、扩展名白名单和随机文件名；对最终 `realpath` 做固定目录前缀校验；导出、导入、删除文件都统一使用安全路径工具。

### B. 数据库同步与跨数据库一致性

#### B-01 [P1] 全量同步界面显示多数据库支持，但 TransferEngine 实际主要是 MySQL 逻辑

位置：

- 前端 `web/js/main.js:112-132`、`3267-3287`：传递并展示 `src_db_type`、`dst_db_type`。
- 后端 `db_transfer_eel.py:319-338`：`TransferEngine` 主要使用 `src_host/src_db`、`dst_host/dst_db`。
- 同步逻辑使用 `SHOW CREATE TABLE`、`SET FOREIGN_KEY_CHECKS`、`INSERT IGNORE` 等 MySQL 语句。

影响：拖拽复制可能有按数据库类型分支，但“数据库同步”入口容易让用户误以为支持任意类型互传。PostgreSQL、Oracle、MSSQL 作为源或目标时，表结构、约束或数据同步可能失败或生成错误 SQL。

建议：

1. 如果全量同步只支持 MySQL/OceanBase，前端明确限制并在后端校验。
2. 如果目标是跨类型同步，抽象统一元数据模型，并为每种数据库实现独立的 DDL、分页读取、批量写入、类型映射和事务策略。
3. 添加 MySQL、OceanBase、PostgreSQL、Oracle、MSSQL 的源/目标矩阵测试。

#### B-02 [P1] 全量同步默认删除目标已有表

位置：`db_transfer_eel.py:333-336`，`web/js/main.js:391-406`、`476-483`。

问题：`TransferEngine` 的 `drop_existing` 默认值为 `True`。前端未传表名时直接启动同步，后端可能删除目标表后重建。

影响：一次误操作可能直接清空目标已有结构和数据，且用户不一定意识到默认行为。

建议：默认改为 `False`；删除模式必须由用户显式选择并二次确认；确认框展示目标连接、数据库、表数量、预计影响和不可逆性；执行前再做一次服务端校验。

#### B-03 [P1] 非 MySQL 类型仍使用 MySQL 表存在判断

位置：`db_transfer_eel.py:913-944` 和 `_dst_table_exists`（约 `279-292`）。

影响：`check_target_tables` 在非 MySQL 连接上仍查询 MySQL 风格的 `information_schema.tables` 或使用 MySQL 字段语义，可能误判表不存在、判断失败，进一步触发错误的创建/删除流程。

建议：按数据库类型实现 `table_exists`，统一返回值和异常语义；不要在公共流程中用 MySQL 实现冒充跨库实现。

#### B-04 [P1] 同步/DDL 中的表注释、自增和默认值需要统一验证

说明：当前工作区已经包含上一轮对拖拽复制 DDL 的修复方向，但功能并非只有拖拽复制一条路径。全量同步、导出、备份、表设计 ALTER、跨数据库转换等路径必须分别检查。

重点位置：

- 拖拽复制和同步 DDL：`db_transfer_eel.py` 中表结构生成相关逻辑。
- 表设计默认值：MySQL 约 `2893-2906`，PostgreSQL 约 `2974-2981`。
- 导出结构：约 `6720-6743`。
- 备份表：约 `3395-3444`。

已发现的具体边界：表设计逻辑使用 `if col.get("default_val")`，空字符串默认值会被当成“没有默认值”。应区分“字段不存在默认值”和“默认值是空字符串/0/False”。

建议建立统一字段元数据模型，明确保存：字段名、类型、长度、精度、是否可空、默认值是否存在、默认值原文、自增、注释、主键、唯一键和排序规则；每条同步路径都从该模型生成目标方言 DDL，并用数据库实际元数据回读验证。

#### B-05 [P2] 全量同步的删除/创建/写入缺少清晰的失败回滚策略

影响：结构已删除、目标表已创建但数据只写入一部分时，用户可能得到半成品目标库。不同数据库的事务和 DDL 提交规则也不同。

建议：把同步拆成“读取快照—生成计划—用户确认—目标预检查—结构变更—数据写入—约束恢复—校验”阶段；记录每阶段状态和可恢复点；支持失败后保留旧表、临时表切换或显式回滚策略。

### C. 导出、导入、表设计与备份

#### C-01 [P1] 导出向导基本是 MySQL 专用

位置：`db_transfer_eel.py:6720-6729`、`6737-6743`。

问题：非 MySQL 类型不读取列信息；随后无论数据库类型都调用 `SHOW CREATE TABLE`。

影响：PostgreSQL、Oracle、MSSQL 的结构导出可能为空、失败或生成错误脚本，字段默认值、注释、自增/序列、约束等也无法可靠保留。

建议：按数据库类型实现结构导出适配器；导出文件中记录源数据库类型和版本；导出完成后使用目标数据库解析/试运行校验，而不是只检查文件生成成功。

#### C-02 [P1] `table_get_ddl` 的 MSSQL 分支使用了错误的获取方式

位置：`db_transfer_eel.py:2389-2510`。

问题：Oracle 有单独分支，其余分支仍调用 MySQL `SHOW CREATE TABLE`，因此 MSSQL 并没有真正的 DDL 实现。

建议：使用 MSSQL 系统目录视图生成字段、默认约束、主键、索引、外键、扩展属性/注释和自增 identity 的完整 DDL；明确区分 MSSQL 和 MySQL，避免使用“其他数据库走默认分支”。

#### C-03 [P1] MSSQL 表设计器信息和应用能力不完整

位置：`table_get_design_info` 约 `2790-2794`；`table_apply_design` 约 `3212`。

问题：MSSQL fallback 只返回空的 `table_options`，没有完整字段、索引等元数据；应用设计时明显支持 MySQL、PostgreSQL、Oracle，MSSQL 最终返回暂不支持。

影响：前端如果显示了 MSSQL 表设计入口，用户可能编辑后才发现无法保存，或者看到不完整信息。

建议：未实现时前端隐藏/禁用入口并明确提示；实现后补齐元数据读取、ALTER 语句、默认约束、identity、索引和事务处理。

#### C-04 [P1] Oracle/MSSQL 备份表方式不能保留完整表结构

位置：`db_transfer_eel.py:3395-3444`。

问题：Oracle 使用 `CREATE TABLE AS SELECT`，MSSQL 使用 `SELECT INTO`。这类复制通常不会完整保留主键、索引、外键、默认值、注释、自增/identity 等对象。

建议：备份表先通过元数据生成结构，再复制数据；对约束、索引、注释和序列/identity 做明确策略。若产品定义只是“数据快照”，名称和界面应明确说明不会复制完整结构。

#### C-05 [P1] SQL 导入单条失败后继续执行，完成提示可能误导

位置：`db_transfer_eel.py:6994-7017`。

问题：每条语句异常后只记录进度并继续；最终仍可能发送完成事件。PostgreSQL 事务进入 aborted 状态后，后续语句通常会全部失败。

影响：用户看到“完成”但实际只导入了部分数据，或整个事务未提交。

建议：提供“遇错停止”和“忽略错误”两种明确模式；统计成功、失败、跳过数量；最终状态至少区分成功、部分成功、失败；保存失败 SQL 和错误原因；根据数据库事务状态执行回滚或重新开始事务。

#### C-06 [P1] SQL 分句器不支持完整数据库方言

位置：`db_transfer_eel.py:6920-6943` 的 `_split_sql_statements`。

不支持或支持不完整的情况包括：

- MySQL `DELIMITER` 和存储过程/触发器。
- PostgreSQL dollar-quoted function。
- SQL Server 批分隔符 `GO`。
- Oracle PL/SQL 多语句块。
- 更复杂的注释、字符串和转义组合。

建议：不要用通用简单扫描器解析所有方言；根据源数据库类型使用对应导出格式/解析器，或者明确限制可导入脚本范围并在导入前做语法检查。

#### C-07 [P2] SQL 文件数据库安全检查不是可靠沙箱

位置：`db_transfer_eel.py:5458-5473`、`6949-6967` 的 `_check_db_prefix`。

问题：只检查有限的带引号数据库前缀，不能覆盖 `USE other_db`、`SET search_path`、未加引号名称、`DROP DATABASE` 等写法。

建议：导入前按数据库类型解析语句并建立允许操作集合；禁止数据库切换和高危管理语句；导入连接本身使用最小权限账户。不要把字符串前缀检查当作安全边界。

#### C-08 [P2] CSV 导入一次性读取全部数据

位置：`db_transfer_eel.py:7045-7058`。

问题：使用 `rows = list(reader)` 后才分批提交。

影响：大文件会造成高内存占用，甚至导致程序卡死或崩溃。

建议：流式读取、按批次提交；限制单行大小和总文件大小；导入前先检查列映射、类型和空值规则。

### D. 任务、并发和资源管理

#### D-01 [P1] 查询状态使用进程级全局变量和无锁字典

位置：`db_transfer_eel.py:204-217`、`1148-1163`、`1233-1264`。

涉及变量：`_query_cancel`、`_query_conn_id`、`_query_src_data`、`_query_jobs`、`_query_result_store` 等。

影响：多个页面或并发查询可能互相覆盖连接 ID、取消标记和结果；一个页面取消查询，可能误影响另一个任务；结果可能串线。

建议：每个任务使用独立 job 对象和唯一 ID，状态、取消事件、结果、异常统一封装；使用线程安全容器/锁，或改用任务队列；所有接口都校验 job 所属会话。

#### D-02 [P1] 全局 `_progress_q` 混用多个任务

问题：导入、导出、拖拽和同步任务共享一个进度队列，启动新任务时多处清空队列。

影响：并发任务可能清除对方进度，前端消费到错误任务的消息，进度显示错乱。

建议：进度队列按 `job_id` 隔离；消息携带任务 ID、阶段、百分比和最终状态；禁止通过清空全局队列来“重置任务”。

#### D-03 [P1] `start_transfer` 没有防止重复启动

位置：`db_transfer_eel.py:891-900`。

问题：新任务会覆盖全局 `_engine` 引用，旧线程仍可能继续运行；`stop_transfer` 只针对当前引用任务。

影响：同一时间启动多个同步时，停止、进度和结果都可能对应错误任务，甚至同时写同一目标库。

建议：用任务注册表管理多个任务；同一源/目标/表加互斥锁；明确是否允许并行；停止时对指定 job 发送取消信号并等待线程退出。

#### D-04 [P1] 轮询任务存在清理不完整和线程线性增长风险

位置：`app/__init__.py:38-51`、`app/routes/__init__.py:45-67` 的 job/poll 逻辑。

问题：结果通常在客户端轮询后移除，但客户端关闭、轮询中断或任务超时时可能残留；watchdog 线程随任务数增长。

建议：统一任务生命周期和 TTL；服务端定期清理过期任务；使用一个后台清理线程或任务调度器，不要每个任务创建长期 watchdog；限制任务数量和结果大小。

#### D-05 [P2] 查询结果依赖前端主动释放，异常关闭时可能长期占用内存

位置：`db_transfer_eel.py:1183-1217` 的 `_query_result_store`。

建议：结果设置最大行数/最大字节数和 TTL；无论前端是否调用释放接口，都由服务端回收；大结果使用临时文件或分页游标。

### E. 前端安全与可维护性

#### E-01 [P1/P2] 多处 `innerHTML` 直接拼接后端消息和数据库对象名称

位置示例：

- `web/js/main.js:49-61`
- `web/js/tree_modules/tree_context.js:239-249`
- `web/js/tree_modules/tree_manage.js:239-248`

问题：虽然部分位置使用了 `escapeHtml`，但不是全覆盖。表名、数据库名、错误信息和后端返回的其他内容可能直接进入 HTML。

影响：恶意数据库对象名称或错误消息可能导致前端 DOM XSS；同时字符串拼接 HTML 也容易造成布局和事件绑定问题。

建议：默认使用 `textContent`/DOM API；确需 HTML 时统一经过可信的严格转义；建立前端安全编码规范并全量搜索 `innerHTML`、`insertAdjacentHTML` 和模板字符串插入点。

#### E-02 [P2] 前端全局变量多、脚本顺序依赖强、缺少自动化检查

问题：前端代码规模较大，主要依赖普通 script 顺序加载、全局状态和字符串拼接，缺少模块边界、类型约束和构建/测试流程。

影响：修改一个同步、连接或树操作功能时，容易影响其他页面；重复定义、加载顺序和状态污染不易发现。

建议：按连接管理、树、同步任务、SQL 编辑器、弹窗等拆分模块；逐步消除全局变量；引入 ESLint/TypeScript 或至少引入 JS 语法检查和基础单元测试。

#### E-03 [P2] 多数据库能力的前端提示与后端实际能力不一致

前端连接选择器显示 MySQL、OceanBase、PostgreSQL、Oracle、MSSQL，但不同功能实际支持范围不一致。建议每个功能根据后端能力返回 capability，并据此禁用不支持的按钮，避免“能选但执行失败”。

## 五、工程化与发布问题

### F-01 [P2] 缺少明确的依赖锁定文件和测试目录

未发现 `requirements.txt`、`pyproject.toml`、`package.json` 或系统化测试目录；依赖主要散落在 `build_release.ps1` 和 `mqdb.spec`。

影响：换机器、升级 Python 或重新打包时容易出现环境不一致；数据库功能缺少自动回归保障。

建议：建立 Python 依赖清单并锁定版本；如继续维护前端，建立前端依赖和检查脚本；增加以下测试：

- 标识符转义和 SQL 生成单元测试。
- 默认值、注释、自增、主键、索引、外键的 DDL 快照测试。
- 各数据库连接和元数据读取集成测试。
- 同步失败、取消、重复启动、断线和部分成功测试。
- 导入脚本危险语句、CSV 大文件和异常编码测试。

### F-02 [P2] 构建脚本硬编码 Python 路径

位置：`build_release.ps1:6`。

问题：固定使用 `C:\Users\92933\AppData\Local\Programs\Python\Python314\python.exe`。

影响：换用户名、换机器或 Python 版本后构建直接失败。

建议：优先使用虚拟环境中的 Python；允许通过参数传入解释器；启动时检查 Python、PyInstaller 和依赖版本并给出清晰错误。

### F-03 [P2] `build_release.ps1` 与 `mqdb.spec` 维护两套打包配置

影响：脚本动态参数与 spec 文件内容可能不一致，导致本地构建、发布构建和后续 CI 行为不同。

建议：选择一种正式构建入口；将资源清单、隐藏导入、版本信息和输出目录集中管理，并在构建后执行启动冒烟测试。

### F-04 [P2] `db_transfer_eel.py` 与 `modules/` 存在重复业务实现

相关模块包括：`modules/transfer_engine.py`、`modules/drag_copy.py`、`modules/export_import.py`、`modules/table_design.py`、`modules/table_ops.py`、`modules/eel_common.py`。

影响：同一 bug 可能只在一个实现中修复。例如拖拽同步的字段属性已修复，但其他同步、导出或表设计路径仍可能缺少相同属性。重复实现也会造成行为、异常和数据库兼容性不一致。

建议：先梳理真实调用关系，再确定一个权威实现；删除或标记废弃代码；用统一元数据模型和共享 DDL 生成器覆盖所有入口。

### F-05 [P2] 多套启动/兼容逻辑和强制退出

位置：`main.py:141`、`app/__init__.py:116` 使用 `os._exit(0)`；另有 `db_transfer_eel.py` 底部启动/fallback 逻辑。

影响：`os._exit` 可能跳过 `finally`、日志刷新、数据库连接关闭和线程清理；多入口会使打包版、开发版和 Flask/Eel 路径行为不一致。

建议：保留一个正式入口，其他入口只做兼容转发；正常关闭使用事件、线程 join 和 `sys.exit`，确保资源释放后退出。

## 六、优先整改顺序

### 第一阶段：先防止数据泄露和误删

1. 为 Flask API 增加 token/会话校验，收紧 CORS，停止自动暴露内部函数。
2. 默认禁止全量同步删除目标表，危险操作增加服务端二次确认。
3. 修复标识符引用和文件路径校验。
4. 密码改为安全存储并清理日志/返回值中的敏感信息。

### 第二阶段：保证同步和导出结果可信

1. 明确每项功能支持的数据库类型，前后端能力矩阵保持一致。
2. 统一字段元数据，覆盖自增、表注释、字段注释、默认值、主键、索引和外键。
3. 为 MSSQL、Oracle、PostgreSQL 分别实现或明确禁用 DDL、导出、表设计和备份功能。
4. 把同步结果区分为成功、部分成功和失败，并增加目标端回读校验。

### 第三阶段：解决并发和资源问题

1. 用 job 对象和 `job_id` 替换全局查询/进度状态。
2. 增加重复任务互斥、取消等待、超时和统一清理机制。
3. 对查询结果和 CSV 导入增加大小限制、分页/流式处理和 TTL。

### 第四阶段：降低长期维护成本

1. 合并 `db_transfer_eel.py` 与 `modules/` 的重复业务实现。
2. 统一启动入口和打包配置。
3. 建立依赖锁定、数据库矩阵集成测试和前端静态检查。
4. 分阶段减少前端全局变量和不安全 HTML 拼接。

## 七、建议的验收标准

整改后至少应验证以下场景：

1. 未携带 token 的本地 API 请求被拒绝；非允许来源不能跨域调用。
2. 普通同步默认不删除目标表；删除模式必须显示明确确认信息。
3. MySQL/OceanBase、PostgreSQL、Oracle、MSSQL 的支持范围在每个功能中明确显示。
4. 同步、拖拽复制、导出、备份、表设计五条路径都能保留并回读验证：自增/identity、表注释、字段注释、字段默认值、空字符串默认值、主键和索引。
5. 目标端写入一半失败时，界面显示“部分成功/失败”，并能看到失败原因和可恢复建议。
6. 两个任务同时运行时，进度、取消和结果互不影响；关闭页面后任务和结果能按 TTL 回收。
7. 大 CSV 不会因 `list(reader)` 一次性读入而导致内存异常。
8. 导入包含存储过程、函数、PL/SQL、`GO` 或 `DELIMITER` 的脚本时，程序能明确支持或明确拒绝，而不是静默拆错。
9. 构建不依赖开发者个人绝对路径，打包后能完成启动、连接、查询和退出冒烟测试。

## 九、总体结论

程序目前具备较完整的数据库管理功能骨架，Python 编译层面没有发现语法错误；但它更像是多个时期功能叠加后的工作版本，还没有形成清晰、统一且可证明安全的产品边界。

最需要优先处理的是：本地 API 无认证、全量同步默认删除、跨数据库能力与实际实现不一致、同步元数据在不同入口不统一、任务状态全局共享，以及明文密码和路径/标识符输入问题。完成这些整改后，再进行模块合并、测试体系和前端工程化，整体稳定性和可维护性会有明显提升。

## 十、本次已实施的修复

本轮已在当前工作区实施以下修复：

- Flask API 增加随机 token、HttpOnly/SameSite cookie 校验；移除任意 CORS；内部函数不再自动注册为 API，业务 API 改为 POST。
- 全量同步默认不删除目标表；拒绝未实现的非 MySQL 全量同步；阻止重复启动同步任务。
- 标识符统一按数据库方言转义，覆盖核心后端和 `modules/` 重复实现；数据库创建、删除、重命名、备份等路径同步收紧标识符拼接。
- 导入临时文件使用安全文件名、随机前缀和目录 realpath 校验；导出文件名清理路径字符。
- 拖拽复制、表设计、导出相关路径统一保留/生成默认值、自增、字段注释和表注释；补充 MSSQL DDL 和表设计元数据/部分 ALTER 支持；修正 PostgreSQL、Oracle、MSSQL 精度/小数位判断。
- 导出和表 DDL 不再无条件调用 MySQL `SHOW CREATE TABLE`；MSSQL 改为读取系统目录生成 DDL。
- SQL 分句支持注释、`DELIMITER`、`GO` 和 PostgreSQL dollar quote；SQL 导入遇错停止并回滚，禁止数据库级管理语句和跨库切换。
- CSV 导入改为流式读取；查询结果增加线程锁、完整 UUID、TTL 回收和按连接取消；移除全局进度队列的强制清空行为。
- 本地配置和树连接数据中的密码使用 Windows DPAPI 加密存储，并兼容旧明文配置迁移读取。
- 修复主要前端后端错误消息直接写入 `innerHTML` 的问题；构建脚本不再依赖开发者个人绝对 Python 路径；正常关闭不再直接调用 `os._exit`。
- 单表和批量拖拽复制均增加进度任务互斥，批量复制调用内部实现，避免单表入口的互斥包装造成误拒绝；SQL Server 表设计、DDL 和备份路径的注释写入改为可重复执行的 extended property upsert。
- Flask 异步 API 改为由单个后台回收线程统一处理超时和 TTL，移除每个请求单独创建 watchdog 线程的做法。
- SQL Server 备份不再使用会丢失 identity、默认值、注释、主键和索引的 `SELECT INTO`，改为先生成结构再复制数据，并在需要时使用 `IDENTITY_INSERT` 保留 identity 数据。
- 增加 `tests/test_core_helpers.py`，覆盖 SQL 分句、标识符转义、默认值、MSSQL DDL 和进度互斥等无数据库单元测试。
- 增加 `requirements.txt` 和 `requirements-dev.txt`，锁定运行时依赖、数据库驱动及 PyInstaller 版本。

验证结果：Python 编译、模块编译、API 鉴权冒烟、SQL 分句器测试、标识符转义测试、DPAPI 往返测试、核心单元测试和 `git diff --check` 均通过。由于当前环境没有真实数据库实例和 Node.js，跨数据库端到端同步、压力测试及 JavaScript 语法检查仍需在对应环境补测。
